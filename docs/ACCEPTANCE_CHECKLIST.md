# Чек-лист проверки по критериям ОренКод 2026

Оценка в критериях ставится от 0 до 3 за пункт; засчитывается только то, что реально проходит на демонстрационном стенде. Этот файл — план проверки, а не заявление о том, что все пункты уже приняты.

## 1. Работоспособность прототипа — 20%

- [ ] **С1 (8):** один аккаунт с несколькими ролями; переключение между кабинетами; API запрещает операции, не разрешённые активной роли.
- [ ] **С2 (8):** Федерация создаёт и публикует соревнование; проверяются дисциплина, тип из справочника, возрастная группа, статус, календарный план и положение.
- [ ] **С3 (10):** спортсмен/тренер подаёт заявку; backend проверяет возраст и дисциплину; Федерация одобряет/отклоняет заявку.
- [ ] **С4 (5):** тренер отправляет запрос на привязку; спортсмен подтверждает; проверить несколько тренеров по разным дисциплинам и историю связи.
- [ ] **С5 (10):** Федерация/назначенный судья вводит результаты; протокол строится по одобренным заявкам; результаты видны в истории спортсмена.
- [ ] **С6 (10):** Федерация назначает судейскую коллегию; судья видит свои назначения и срок категории; подаёт заявку на категорию; Федерация принимает решение.
- [ ] **С7 (10):** спортсмен без тренера или тренер подаёт заявку на разряд с указанием соревнования и результата; Федерация фиксирует решение; уведомления о сроке получают спортсмен, тренер и Федерация.

## 2. Соответствие функциональным требованиям — 20%

- [ ] **С8 (16):** реестр связан с организацией, дисциплиной, годом начала занятий и этапом подготовки; отчёт показывает динамику минимум за два года, разрезы по организациям/дисциплинам/возрастам/муниципалитетам и корректно выгружается в XLSX.
- [ ] **С9 (20):** рейтинг фильтруется по дисциплине и возрасту; очки прозрачны и соответствуют уровню соревнования и месту; коэффициент стабильности ×1,2 применяется при призовых местах минимум на двух соревнованиях; дисквалифицированные исключаются; состав сборной редактируется из рейтинга; формируется список и проект приказа.
- [ ] **С10 (10):** документы по заданным формам: протокол соревнования и отчёт по спортсмену; проверить содержимое, а не только скачивание.
- [ ] Дополнительные пункты Д3–Д12 оценивать отдельно только после демонстрации работающего сценария; наличие пункта в меню не считать реализованной функцией.

## 3. Технологичность — 20%

- [ ] **Т1 (10):** повторяемый запуск, модульная структура, документированное API, серверная проверка ролей, безопасное хранение паролей/сессий, понятный README.
- [ ] **Т2 (10):** связи и ограничения БД согласованы, нет «висячих» ссылок, есть реалистичные демонстрационные данные по всем шести дисциплинам и история минимум за два года.
- [ ] **Д1 (5):** региональный ФСП ID — оценивать только если работает заявленный сценарий единого входа.
- [ ] **Д2 (5):** Telegram — проверить фактическую доставку уведомления и работу long polling; конфигурационный экран сам по себе интеграцией не является.
- [ ] **Telegram linking:** выдать восьмизначный код в разделе «Уведомления»; привязать его командой `/link КОД`; убедиться, что код действует 10 минут и одноразовый; отключить связь из UI.
- [ ] **Telegram messages:** проверить персональные сообщения о решении по заявке, решении по разряду, решении по судейской категории и публикации результатов. Общий чат проверять только при настроенном `TELEGRAM_DEFAULT_CHAT_ID`.

## 4. Презентация — 20%

- [ ] **П1 (10):** понятная демонстрация сквозного сценария от соревнования до результата/рейтинга, без перехода на несвязанные макеты.
- [ ] **П2 (5):** команда объясняет архитектуру, бизнес-правила и соответствие регламентам.
- [ ] **П3 (5):** фирменная стилистика ФСП, адаптивность, навигация, доступность, понятные пустые состояния и подсказки.

## 5. Потенциал — 20%

- [ ] **Р1 (10):** термины и процессы соответствуют спортивному программированию; корректны возрастные группы, статусы, типы соревнований, календарные планы и сроки разрядов/категорий.
- [ ] **Р2 (10):** собственный сценарий команды даёт практическую пользу и работает на данных платформы.

## Что уже изменено в этой сборке

- Добавлен официальный SVG-логотип ФСП в экран входа, загрузку сессии и боковую панель.
- В рейтинге добавлен фильтр по возрастной группе; места в отображаемой выборке пересчитываются после фильтрации.
- Форма создания соревнования расширена: уровень, формат, возрастная группа, срок заявок, календарный план и номер, положение.
- В сборной добавлен выбор спортсменов из рейтинга, фильтры по дисциплине/возрасту/минимальному разряду и сохранение состава в API; список/проект приказа должны проверяться на сохранённом составе.
- Кнопки документов подключены к существующим API для протокола (DOCX/XLSX), отчёта спортсмена (DOCX), реестра (XLSX), отчёта о численности (XLSX) и проекта приказа (DOCX).
- Добавлены темы «Авто / Светлая / Тёмная», системное определение `prefers-color-scheme`, сохранение ручного выбора и управление темой с экрана входа и из рабочей панели.
- Убраны фиксированные бейджи «12» и «3» из меню, поскольку они не были привязаны к реальным счётчикам.
- Убраны фиктивные изменения статистики вроде «+8,4%» и «12 новых»; карточки больше не выдают эти числа за аналитику из базы.
- Статус источника данных различает успешную загрузку API и резервные демонстрационные данные.

## Важные ограничения, требующие отдельной проверки

- В интерфейсе пока нет полноценного пользовательского рабочего места для ввода результатов и просмотра назначений судьи; часть процессов доступна только через API.
- Сценарии XLSX, протокола и отчёта спортсмена должны быть проверены на фактическом файле и сравнены с формами заказчика.
- Точность рейтинга, исключение дисквалифицированных и расчёт коэффициентов нужно подтвердить тестовыми наборами данных.
- Для С4 (привязка тренер—спортсмен), С5 (ввод результатов), С6 (назначение судей/заявки на категории) и С7 (заявки на разряды) часть серверных обработчиков есть, но полноценные рабочие формы этих процессов в интерфейсе ещё не завершены. Их нужно тестировать через API либо доработать UI перед обещанием полного покрытия.
- Внешняя доставка уведомлений через Telegram должна быть проверена с настоящим токеном и работающим long polling; локальный запуск не требует публичного webhook.
- Региональный ФСП ID не считать полноценным OIDC-провайдером без проверки authorization code + PKCE, discovery и userinfo; дополнительный функционал D3–D12 также оценивать только при наличии реально работающего сценария.
- Перед итоговой оценкой нужно запустить `docker compose up --build` и пройти все отмеченные выше сценарии на одном стенде.
