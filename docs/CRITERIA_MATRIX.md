# Сверка проекта с критериями ОренКод 2026

Дата предварительного аудита: 27.10.2026. Основание: `Критерии_оценки_ОренКод_2026.pdf`, `КЕЙС_ОренКод_2026_Цифровая_платформа_ФСП.pdf` и текущие исходники проекта.

> Это аудит исходников, а не присвоенные баллы. По правилам кейса оценивается только то, что реально работает на демонстрационном стенде. Пока проект не прошёл полный запуск и сквозной прогон, ни один пункт нельзя честно отмечать как подтверждённый на 3/3.

## Сводка

Все пять критериев имеют равный вес — 20% каждый: работоспособность, функциональное соответствие, технологичность, презентация и потенциал. Внутри критериев пункты оцениваются от 0 до 3.

| Приоритет | Что есть сейчас в исходниках | Основной разрыв до уверенной демонстрации |
|---|---|---|
| P0 | Роли и авторизация, создание соревнования, заявки и модерация, рейтинг/сборная, документы и уведомления имеют UI или API | Завершить сквозные пользовательские процессы и проверить их на одной базе, не только наличие endpoint |
| P0 | Есть backend-сценарии привязки тренера, результатов, судейских назначений, разрядов и категорий | Для С4–С7 не хватает полноценных пользовательских экранов; нужно убрать необходимость ручного вызова API |
| P0 | Есть Telegram long polling, чтение соревнований/рейтинга, конфигурация внешнего канала | Нужны настоящий бот, подключение аккаунта и проверка реальной доставки сообщений |
| P1 | Есть реестр и XLSX-отчёты, фильтры рейтинга, выбор состава сборной и проект приказа | Сверить численность с источником данных, формулу рейтинга и документы с регламентом/формами заказчика |
| P1 | Go API, PostgreSQL, миграции, Docker Compose, OpenAPI, README, серверная ролевая проверка | Полные сборка и тесты, контроль ошибок, тесты прав, безопасные production-настройки и журналирование каждого критичного действия |
| P2 | Частичные API/заготовки D6, D10, D11 | Превратить их в доступные сквозные пользовательские сценарии; выбрать ограниченный дополнительный сценарий вместо поверхностной реализации всех Д3–Д12 |

## 1. Работоспособность прототипа — 20%

| Критерий | Статус по коду | Что уже прослеживается | Что осталось сделать |
|---|---|---|---|
| **С1 (8)** Несколько ролей и переключение | Есть основа | Учётные записи, активная роль, переключение роли, middleware с проверкой роли на защищённых маршрутах | Прогнать один аккаунт с 2+ назначенными ролями; доказать запрет каждой запрещённой операции прямым API-запросом |
| **С2 (8)** Создание и публикация соревнования | Есть UI + API | Форма и API содержат тип, дисциплину, возрастную группу, статус/формат, календарный план, положение; отдельная публикация | Пройти создание → изменение статуса → появление в календаре → уведомление; проверить справочники и ошибки валидации |
| **С3 (10)** Заявка и модерация | Есть UI + API | Заявка, проверка возрастной группы/дисциплины, решение Федерации, статусы | На стенде проверить отрицательные случаи, повторную заявку и то, что участник не видит чужие данные |
| **С4 (5)** Привязка тренера и спортсмена | Частично: backend | API для запроса привязки и подтверждения спортсменом | Сделать в интерфейсе тренера и спортсмена: запрос → подтверждение/отказ → отображение активной связи; проверить ограничение по дисциплине |
| **С5 (10)** Результаты, протокол, история | Частично: backend + экспорт | API сохранения результатов, проверка одобренных заявок, протокол и история выступлений; Telegram-уведомление о публикации добавлено в исходники | Нужна полноценная форма ввода результатов; проверить расчёт мест/баллов, сохранение, автопротокол и историю от имени спортсмена |
| **С6 (10)** Судейская коллегия и категории | Частично: backend | Назначения судей, список назначений/срок категории, заявка и решение по категории | Сделать кабинет судьи и экран Федерации; проверить просроченную категорию, запрет ввода результатов неназначенным судьёй и уведомления |
| **С7 (10)** Разряды и сроки | Частично: backend | Заявка на разряд, решение Федерации, запись разряда и даты истечения; Telegram-уведомление о решении при привязанном аккаунте | UI для заявки/решения и тренера/спортсмена; автоматическое плановое предупреждение о приближении срока пока не подтверждено как рабочий процесс |

## Приоритетная очередь

1. **Telegram как внешний канал и собственный сценарий:** завершить привязку аккаунта, уведомления о решениях/результатах и реальную доставку. Это напрямую помогает обязательному требованию внешних уведомлений и потенциально Р2.
2. **С4–С7:** сделать пользовательские экраны привязки тренера, ввода результатов, назначений/категорий и разрядов; иначе эти процессы трудно показать на стенде.
3. **С8–С10:** проверить реальные файлы и статистику; утвердить формулу рейтинга/сборной у заказчика.
4. **Т1/Т2 и контрольный прогон:** чистая установка, тесты, права, миграции, демонстрационные данные и README.
5. **Только затем выбрать одну дополнительную механику:** разумный кандидат — Д10 (справка + QR + публичная проверка) или Д6 (сводная страница развития региона). Д3/Д4/Д8 крупнее и потребуют значительного времени.

## Доказательства для демонстрации

Для каждого пункта нужно приложить конкретное доказательство: короткое видео/скрин, endpoint и успешный/ошибочный запрос, сформированный файл, либо данные до и после действия. Состояние «кнопка есть», «эндпоинт есть» или «записано в README» не равно рабочему сценарию.
